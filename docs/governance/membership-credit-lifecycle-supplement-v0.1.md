# 成员资格、积分语义与账户生命周期补充说明（v0.1 草案）

> **性质**：对 [管理制度草案 v1.0 Alpha](management-regulations-draft-v1.0-alpha.md) 与 [白皮书 v1.0 Alpha](../whitepaper/linkrsp-whitepaper-v1.0-alpha.md) 中已述原则的**系统层延伸**；**不构成法律意见**，具体法域下的合规与产品条款须单独评审。  
> **约束**：LRS 积分在协议语义上为**权益与优先权凭证**，**非货币**、**非证券化兑付承诺**；本文不引入「积分转让、继承」作为协议义务。  
> **工程状态**：下文中的状态机、冻结策略等多为**规格预留**；当前开源实现未必已覆盖全部字段与接口，以 [实施计划 v1.0](../engineering/implementation-plan-v1.0.md) 为准。

---

## 1. 「1+1」双轨与社区拓扑变化（N→S、S→N）

### 1.1 合法态与非法态

- **合法态（意图）**：在同一治理周期内，每个 UID 的**有效关联**至多 **1 个 S 型社区**与 **1 个 N 型社区**（与管理制度一致）。  
- **非法态（须消除）**：例如用户已关联一个 S，而其原 N 型社区完成 IPO **升格为 S**，若不做处置，将出现**两个有效 S 关联**，与 1+1 冲突；或出现其他违反双轨计数约束的组合。

### 1.2 协议层最小要求（原则）

- **不可持续违规**：系统在检测到非法态时，应进入**协调态**（概念名示例：`reconciliation_required`）：在用户或治理流程完成处置前，对**会产生新的违规结算或关联边**的写路径予以**限制或冻结**（具体范围由后续 spec 冻结：例如禁止新任务发布、禁止新结算提交等）。  
- **可审计**：任何 IPO、降级、用户主动切换导致的关联变更，应能对应到**带时间戳的事件**与（若已实现）审计记录。

### 1.3 处置机制（治理择一 + 公示）

以下选项**不**由本文档代社区拍板；维护者应在 Judge/章程中**择一并公示**：

1. **迁移窗口**：IPO 生效前公告 T 日；窗口内用户须**主动选择**保留哪一个 S 关联或退出其一。  
2. **窗口结束默认策略**：例如保留「登记在先」的 S 关联、或保留「用户声明优先」的关联（须在章程中写明）。  
3. **S→N 降级**：原 S 关联终止或转为**历史只读**；是否自动释放「S 槽位」、是否允许立即加入新 S，由治理定义**冷却期**（与管理制度中「身份切换冷却期」并列：冷却期防**洗分**；拓扑变化防**双 S**——二者可同时存在）。

### 1.4 成员资格边（工程建模建议）

建议将会员与社区的关系建模为**边**，而非仅快照字段，并保留：

- `valid_from` / `valid_until`（或等价语义）；  
- `reason`：`user_switch` | `community_ipo` | `community_demotion` | `admin_correction` 等。

规则引擎按**时间轴**判定 1+1，可避免「仅看当前行」的歧义。

### 1.5 与「身份切换冷却期」的关系

管理制度中的**冷却期**用于抑制频繁换社区带来的套利与洗分风险；**本节拓扑协调**用于处理 **IPO/降级导致的结构突变**。两者应同时保留，并在未来 spec 中写明**适用顺序**（例如：先解决非法态，再适用冷却期）。

## 2. 积分与社区切换、跨形态任务

### 2.1 账本事实层（不可因迁移而改写历史）

- 已落库的积分分录（如 `ledger_entries` 类事件）遵循**只追加**原则：不因用户更换社区、社区降级而**删除或原地修改**历史行。  
- 历史分录所关联的 `community_id` / 任务上下文保持**当时真相**，供审计与回放。

### 2.2 解释层与「可用性」语义（非余额搬家）

- **非语义**：将某一社区的积分余额「整体搬迁」至另一社区，或按固定汇率做「跨社区余额兑换」，易与**权益凭证**定位冲突，且难以审计公平性。  
- **推荐语义**：在全局 UID 之下，使用**带 scope 的投影视图**（示例维度：`community_id`、任务类型、`ΣW_risk` 桶、滑动时间窗）。**接单资格、排序权重、展示给第三方的「可用积分」**可由规则限定为「仅统计某 scope 内分录」，而非单一全局标量。  
- **跨行业 / 异质社区**：不同 S 社区的行业与风险结构不同，**不应**默认「历史积分完全可比 → 自动获得新社区同等接单资格」。新社区可要求**新证据链**或**新窗口内**的累积；具体门槛由社区自治与披露解决，协议提供**查询与规则钩子**。

### 2.3 与白皮书、管理制度措辞的对齐

- 白皮书与管理制度中关于「硬/软积分」「影子系统」的表述，重在**叙事与激励分层**；本文强调工程上须区分**历史分录事实**与**当下可用性解释**，避免公众将积分误解为**可任意跨社区通兑的等价物**（仍非货币，见 C-1）。  
- S 级语境下「更具调度意义的权益」宜理解为：**在规则允许的范围内**参与排序与资源分配，而非无边界「通用购买力」。

## 3. 老龄化、信任、账户终止与数据留存

### 3.1 积分与「当下可服务能力」

- 积分反映的是**历史可审计贡献**在规则下的量化投影，**不**等同于持有人当前的体力、健康或特定照护场景的适配度。  
- **任务匹配**应允许引入**任务属性**（风险等级、体力要求、资质等）与**社区策略**；协议层不承诺「积分高则必然适合某类陪护任务」。

### 3.2 休眠、身故与权益终止

- 建议区分账户状态（概念）：**活跃** / **休眠（dormant）** / **归档（archived）**（用语可随工程表结构调整）。  
- **权益语义**：积分所代表的协议内权益**不**作为可继承财产处理；主体消灭或账户按治理规则终止后，**不再产生新的权益行使**（与「非继承」叙事一致）。  
- **数字遗产**：若未来提供账号委托、数据导出或纪念性只读档案，属**产品与合规层**设计，须单独条款；**不得**表述为积分本身的财产传承。

### 3.3 数据留存与存储成本

- **分级留存**：热数据（近期任务与审计）与冷归档（历史分录、摘要化证据索引）分层；重媒体对象与元数据分离，控制对象存储体量。  
- **摘要与哈希**：长期保留可优先保留**审计摘要、哈希与关键元数据**，原始证据按治理设定的保留期降级或删除（须符合届时适用法律与用户协议）。  
- **法域**：境内上线、备案与个人数据删除请求等，以 [实施计划 v1.0](../engineering/implementation-plan-v1.0.md) 中 Phase G 及专门合规评估为准；本文仅列**设计原则**。
